# Especificación de Refactor Blueprint v1.9

Basado en el archivo [blueprint.json](file:///home/rmonla/Documentos/GitHub/rm-DiploIA_TPFI/www-dtic-gema/assets/docs/blueprint.json), se proponen los siguientes cambios estructurales en el escenario de Make.com.

## 🛠️ Cambios en el Escenario

### 1. Módulo Inicial: Receptor (Webhook)
- **Cambio**: El módulo ID 3 ya recibe `session_id`. No requiere cambios estructurales, solo asegurar que se mapee en los pasos siguientes.

### 2. Módulo de Autenticación (Google Auth Verified)
- **Táctica**: El webhook ahora recibirá un `gmail_verified_email`.
- **Mapeo**: Utilizar este email como llave primaria para todas las búsquedas.

### 3. Búsqueda de Historial (Google Sheets)
- **Módulo**: `Google Sheets: Search Rows` en la pestaña `Tickets`.
- **Filtro**: `Email == {{gmail_verified_email}}` y `Estado != "Cerrado"`.
- **Orden**: Descendente por Fecha para obtener el más reciente.
- **Resultado**: Almacenar en una variable `last_ticket_info` (ID, Estado, Tema).

### 4. Orquestador Gemini (Proactividad)
- **Inyección**: El prompt ahora recibe:
  - `user_name`: Del perfil de Google.
  - `last_ticket`: El objeto recuperado en el paso anterior.
- **Humanización**: El orquestador usa estos datos para el saludo inicial "Cyber-Luxury".

### 5. Responder (ID 7) - Salida Estructurada
- **Formato**: Devolver el objeto JSON completo según [v1.9-system-prompt.md](file:///home/rmonla/Documentos/GitHub/rm-DiploIA_TPFI/data/memoria/1.9-dev/v1.9-system-prompt.md).

## 🔗 Vínculo con Frontend
- El frontend ya está preparado para recibir `data.response` y `data.meta`.
- El blueprint debe devolver ahora un objeto JSON en el módulo **Responder (ID 7)**.

```json
{
    "response": "{{11.text}}",
    "ticket_id": "{{6.ID_Ticket}}",
    "meta": {
        "intent": "{{Clasificador.text}}",
        "session_id": "{{3.session_id}}"
    }
}
```

---
> [!TIP]
> Esta estructura permitirá que GEMA "recuerde" lo que se habló hace dos mensajes dentro de la misma sesión.
